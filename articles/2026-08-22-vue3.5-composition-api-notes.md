组合式 API 最大的变化不是写法，是「逻辑的组织方式」：相关逻辑不再被 data/methods/computed 切成四段，而是住在一起。

## 状态放哪

判断标准只有一条：谁的生命周期该管它。全局状态在根组件挂载一次，子组件 useXxx 拿到同一实例：

```ts
// src/composables/usePostList.ts —— 模块级单例
const sharedCount = shallowRef<number | null>(null)

export function usePostList() {
  // 没有实例才初始化，跨路由保留状态
  sharedCount.value ??= ref(PAGE_SIZE)
  return { visibleCount: sharedCount }
}
```

这个模式救过一次命：列表页「加载更多」的进度，原来放在组件里，进详情返回就丢。状态提升成模块级单例后，跨路由天然保留。页面局部状态（表单、弹窗开关）就老老实实留在页面组件里，别滥用单例。

## 什么时候抽 composable

> composable 抽取的时机是第二次重复，不是第一次出现。

第一次写逻辑时直接内联，第二次遇到相同需求再抽。提前抽象的代价是接口猜错导致的返工，重复两次的代价只是复制粘贴，后者便宜得多。

## 类型体验

defineProps 泛型写法让 props 类型零冗余：

```ts
const { post } = defineProps<{ post: Post }>()
const relativeTime = computed(() => formatRelativeTime(post.publishedAt))
```

computed 自动推导返回类型，ref 在模板里自动解包，TS 全程无断言。类型即文档，重构改 Post 接口时，所有受影响组件编译期全部标红，一个都漏不掉。

## 一个提醒

组合式 API 不等于「所有东西都抽成函数」。组件内三五行的一次性逻辑，封装只会增加跳转成本。组合式解决的是逻辑复用和组织，不是逼你写更多函数。
